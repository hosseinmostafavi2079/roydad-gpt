# Payment architecture (Phase 6 work in progress)

EventOS keeps financial records inside each tenant database. A program run holds the current server-side price; enrollment copies that price into a payment snapshot. The browser never supplies the amount, currency, discount, participant, or final payment state. A paid enrollment reserves capacity as `AWAITING_PAYMENT` for 15 minutes; a free enrollment retains the existing direct confirmation path.

## Provider boundary

`src/modules/payments/provider.ts` defines the adapter contract and capability flags. `registry.ts` contains only adapters shipped by the application operator. The current `TEST` adapter is for local development and CI. The registry rejects it in production, except for the explicitly marked, isolated Playwright test server using the existing E2E preload marker; it has no ordinary production activation path. Real gateway sandbox mode is a future adapter-specific setting and is distinct from EventOS TEST. No real gateway is installed yet.

Adapters receive internal `paymentId` and `paymentAttemptId`, trusted amount/currency, typed configuration, and a server callback URL. They return normalized states plus separate authority, transaction, and reference identifiers. Provider-specific statuses and signatures are mapped inside the adapter. `operations.ts` checks redirect and server-verification capabilities, verified amount/currency, status lookup, and refund capabilities without recognizing provider names. The unit suite registers a second fake adapter with different capabilities to exercise this boundary.

The platform allowlist is stored in the control database. Tenant configuration is stored only in its database as AES-256-GCM ciphertext, authenticated with tenant ID and provider key. An attempt stores its own encrypted configuration snapshot so an in-flight callback or webhook can be verified after the active configuration changes. Webhook adapters first extract an untrusted authority solely to locate the attempt, then verify the signature using that attempt's configuration snapshot. The existing dedicated tenant bootstrap encryption key derives a separate payment-config key. Neither APIs nor audit events return configuration plaintext. Each adapter defines a strict schema; the TEST adapter accepts only an empty object.

## Lifecycle and accounting boundary

`payments` holds a price/discount/currency snapshot per enrollment. A coupon may set the discount before the first provider attempt; after checkout begins, the snapshot cannot change. `payment_attempts` preserves every provider attempt, including failures and expiry, and carries provider references separately. The callback route resolves the tenant from the host, matches the provider and attempt, then invokes server-side adapter verification. A browser callback alone never marks payment successful. Verification updates the attempt, payment, enrollment, invoice, and redacted audit record in one tenant transaction. Duplicate successful callbacks are idempotent. A verified payment arriving after a reservation expires remains recorded and invoiced but does not automatically confirm an enrollment whose capacity may have been reused; an operator must resolve it.

Coupons are reserved under a row lock before checkout, and their discount becomes part of the payment snapshot. Reservations move from `ACTIVE` to `REDEEMED` only after verified payment or a full-discount, zero-due checkout; expiration moves them to `RELEASED`. Only redeemed coupons increment `used_count`, while active reservations count against the limit. Expiration changes an unpaid enrollment to `EXPIRED`, releasing its capacity without deleting the attempt or other financial history. Cleanup and verification lock the payment and enrollment rows in the same order. If verified success arrives after expiration, the payment and invoice record the funds, but enrollment stays expired and a released coupon remains released. An operator must resolve that exception because capacity may already have been reused.

The schema also includes refunds, invoices, and a unique provider-event identity. The generic webhook route requires an adapter to verify its signature and normalized result; TEST does not use webhooks. The payment maintenance worker runs every 60 seconds, takes a control-database advisory lock to prevent overlapping cycles, walks tenants in bounded pages, expires reservations in bounded batches, then reconciles unresolved attempts in bounded batches. Reconciliation queries only adapters declaring status-query capability, may be narrowed to one provider, skips settled payments, and backs off failed status lookups using `next_reconcile_at`. The one-shot command is `pnpm worker:payments:once`; the continuous command is `pnpm worker:payments`. Logs include tenant, payment, provider, normalized result, and job ID without provider secrets. Payment API refunds and explicit manual refunds have different methods and records. Manual refunds require an operator, reason, and reference, and cannot be silently substituted for an adapter API call. Financial snapshots and invoices are historical records; price changes on a run do not recalculate them.

Adding a gateway should require a typed adapter, registry entry, and any adapter-specific configuration UI. Enrollment, invoice, coupon, capacity, refund, and participant tables do not encode gateway-specific fields. Provider authority, transaction, and reference fields and encrypted per-attempt configuration are already present. A future provider should not require changing those core tables. Gateway-specific asynchronous semantics, provider event verification, and settlement lookup must be implemented in that adapter and then wired to the generic processing path.

## Operator and participant views

The Persian RTL finance area provides an overview, filterable transactions, invoices with private PDF downloads, coupons, refunds, and payment provider settings. Participant account pages show their own payments and invoices; the payment result page reads stored server state. The TEST adapter supports deterministic local/CI success, failure, pending, invalid signature, amount mismatch, duplicate callback, and refund outcomes without an external gateway. No production payment provider is installed. Keep payments disabled for production tenants until a real adapter is configured and the GitHub gate passes.
