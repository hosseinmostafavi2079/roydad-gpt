# Security

## Controls in the implemented phases

- Treat platform administration, provisioning credentials, tenant databases, identities, sessions, grants, and domain mappings as privileged assets.
- Validate configuration, hosts, request bodies, identifiers, and status transitions at trust boundaries. Tenant mutation inputs use strict schemas and explicit allow-lists.
- Enforce platform and tenant authentication/authorization in server-side operations with separate identity stores and default-deny policies. There is no public platform or tenant sign-up.
- Use Argon2id password hashing and server-managed sessions. Platform administrators require TOTP MFA in production. Tenant sessions are host/tenant-bound, use secure HTTP-only SameSite cookies, rotate through the auth library, and are rechecked against current tenant/user status and grants on protected requests.
- Apply authentication throttling and generic login/invitation errors. The login path only queries the tenant resolved from the trusted host; it never searches other tenants by email.
- Tenant Google OAuth uses Better Auth's Google provider on an exact allow-list of tenant origins (`GOOGLE_OAUTH_ALLOWED_ORIGINS`). Each allowed tenant origin needs its `/api/tenant-auth/callback/google` URI registered with Google. The client ID and secret are server environment values. Better Auth validates OAuth state and uses PKCE. Implicit linking requires both Google's verified email and the existing local account's verified email; mismatched emails and unverified identities cannot link. OAuth tokens are encrypted at rest. The signed Google identity mock is accepted only by the isolated Playwright server marker and is unavailable in ordinary production. Event return paths accept only local event/account paths.
- Tenant Google sign-in additionally requires the tenant's explicit `google_login` feature. The server denies OAuth initiation and callback when that feature or exact origin configuration is absent. The signed E2E identity override is restricted to the isolated test server on a `.localhost` tenant origin. `/auth/continue` resolves the tenant from the hostname, reads role assignments from the tenant database, and sends participant-only accounts to a validated event path or `/account`; other tenant roles go to `/dashboard`. Client-supplied roles and external return URLs are ignored.
- Invitations use random 32-byte base64url tokens, store only a SHA-256 token hash, expire after 24 hours, and are consumed transactionally once. The invitation mail interface uses explicit `MAIL_TRANSPORT=smtp|test`, defaulting to SMTP. Production configuration rejects `test` unless the private Playwright preload is active, requires TLS SMTP, and fails safely if delivery is unavailable. The outbox captures messages only in tests without an application read route; its temporary file is mode 0600 and removed by test teardown. Tokens are never logged or returned in production APIs. Owner bootstrap data is encrypted with a dedicated production key.
- Roles and permissions are tenant-local normalized relations. Effective permissions are current role unions. Role APIs limit grants to the actor's authority, system roles are protected, and the last active Organization Owner is preserved.
- Resource authorization checks tenant context and supports explicit relationship constraints. Phase 3 business relationships and their detailed scopes remain unimplemented.
- Separate control-plane, tenant-runtime, and provisioning/migration credentials. Never expose secrets to browser code or logs. Generate database identifiers from immutable internal IDs and parameterize SQL values.
- Resolve tenant context only from normalized trusted host mappings. Require verified custom domains and an active tenant. Bound tenant pools and provisioning work; serialize migrations, invitation races, and protected-owner changes where needed.
- Phase 4 public reads use only the trusted hostname tenant context and published active programs. Registration form answers are validated against a versioned allowlist and saved with the schema snapshot. Enrollment locks the run row in PostgreSQL before counting confirmed seats and inserting a unique tenant/run/participant registration, so concurrent requests cannot oversell. Organizer listing and CSV export require tenant-local enrollment permission; CSV values are quoted and spreadsheet formula prefixes are escaped.
- Tenant participant sign-up uses Better Auth password hashing and email verification. Email OTP uses Better Auth's hashed, expiring, single-use challenge with send and verification limits; tenant-specific auth secrets bind challenges to the resolved tenant. Mail uses the explicit provider setting and the production configuration rejects test delivery. Public profile colors, URLs, and presentation choices are validated as typed values, with no arbitrary HTML, CSS, or JavaScript input.
- Audit security-sensitive changes transactionally with tenant/actor/target/request IDs. Exclude passwords, hashes, tokens, connection strings, cookies, and personal data from logs/audit details. Tenant audit entries are append-only.
- Keep CSP, HSTS in production, `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, and `frame-ancestors` configured and verified against application asset needs.
- Return generic errors with request IDs. Unexpected authentication-handler exceptions are caught at the API boundary and logged only with error class and request ID.

## Security verification

Organization media uses private S3-compatible object storage. Object keys include the trusted tenant ID and randomized names; clients cannot choose the tenant path. Uploads validate supported MIME types, file signatures, and per-file size before storage. Tenant permissions and storage limits are enforced server-side. Public media reads resolve the tenant from the trusted host and verify tenant-local metadata, so a media URL from another tenant returns 404. Production S3 uploads request server-side AES256 encryption; local S3Mock is a disposable test/development service and does not provide production security guarantees. Never expose storage credentials to browser code or commit local generated credentials. Website settings accept typed URLs, colors, and presets, not arbitrary CSS or JavaScript.

See `docs/TESTING.md` for unit policy tests, real-PostgreSQL migration/authentication/RBAC/isolation/race tests, and Playwright access-boundary tests. CI also runs dependency audit, Gitleaks, and CodeQL. Local dependency audit and targeted Gitleaks results must be checked at each release. Unresolved exploitable high/critical findings block release.

Pilot Step 2 creation accepts only a validated platform-admin request and same-origin mutation. A UUID creation key is unique per administrator and bound to a SHA-256 payload hash, so repeat submissions reuse one tenant/job without exposing the initial owner bootstrap. The slug schema excludes host separators; the generated database identifier comes from an internal UUID. Worker health checks report only state and safe phase/error/request IDs. Optional platform-admin logo upload resolves an active tenant by its stored primary hostname, validates image signature and storage quota, writes a tenant-prefixed private S3 object, and updates only that tenant's website profile. The old object is removed after commit. An already pending owner invitation is revoked before an authorized resend; only the newest token remains valid. Invitation tokens and mail credentials are never returned to the browser.

## Known limits and operational requirements

This repository has no production deployment claim. Production still requires managed secret storage, key rotation, backup and restore exercises, infrastructure/network review, monitored rate limits, and a deployment-specific MFA enrollment/recovery runbook. Use a unique production `TENANT_BOOTSTRAP_ENCRYPTION_KEY` of at least 32 characters; production configuration rejects a missing/short key. Do not reuse development placeholders. Instructor/program/session ownership relationships and other Phase 3 object scopes must be implemented before those business resources are exposed.
## Phase 3 scheduling and demo boundaries

Phase 3 APIs resolve the tenant before opening its database, enforce permissions on the server, and check instructor object membership for run/session reads. Tenant-local composite foreign keys and queries prevent foreign tenant identifiers from becoming valid assignments. Scheduling writes serialize per tenant inside PostgreSQL transactions before checking room and instructor overlap. Audit events contain identifiers and actions, not credentials or invitation tokens. The local demo scripts refuse production and CI, require a loopback PostgreSQL host, and keep generated passwords only in an ignored local file. No demo credential route exists.

## Attendance and certificate controls

Attendance routes require current tenant grants and feature flags. Assigned-session instructors cannot read unrelated sessions. Participant self-service queries are bound to the authenticated participant ID. Marking checks confirmed/completed enrollment inside a transaction and updates one row per participant/session. CSV exports escape spreadsheet formula prefixes. QR challenges use a derived HMAC key, short expiry, tenant/session binding, active session window, and transactional replay uniqueness; the QR token is excluded from audit entries and request URLs.

Certificate issuance requires a completed run, valid enrollment, template permission, and available tenant storage quota. Template text allows only named placeholders and never executes HTML. Uploaded backgrounds are size, MIME, and signature checked. PDFs and images are private S3 objects under tenant-derived paths, and PDF download requires current tenant authorization plus ownership or staff read permission. Random verification codes have 192 bits of entropy; public lookup is tenant-scoped, rate-limited, and returns only name, program, serial, and issue date for active certificates. Revocation immediately removes the public result and blocks PDF download. No storage credentials or verification codes are logged or returned by list APIs.
# Payment provider boundary

Payment provider configuration is tenant-scoped and encrypted at rest with AES-256-GCM using a domain-separated key derived from the dedicated tenant bootstrap encryption secret. Tenant and provider identities are authenticated as associated data. APIs and audit records expose only provider keys, enablement, normalized states, and financial amounts; they do not expose secret configuration. Platform allowlisting and tenant payment feature flags are checked before activation. EventOS TEST is rejected by the registry in ordinary production; only the isolated Playwright server's existing E2E preload marker permits it during CI/browser testing. Browser callback parameters are never accepted as proof of payment; the adapter must verify server-side and the paid amount/currency must match the stored server snapshot before transactional confirmation. Expiration and verification serialize through payment and enrollment locks; a late verified payment is recorded and invoiced without claiming released capacity or coupon use. Participant payment and PDF lookups enforce authenticated owner and tenant boundaries. Reconciliation uses only declared provider capabilities, bounded work, backoff, and redacted logs. Production payments remain disabled until a real provider is configured and the GitHub gate passes.

# Pilot Step 3 public content boundary

Public website configuration accepts enumerated templates, sections, menu entries, layout controls and bounded color/font tokens. URLs for editor CTAs and custom page blocks are validated local paths; no arbitrary HTML, JavaScript or CSS is accepted. Information page inline formatting is interpreted into escaped React text and elements. Mutation routes require a tenant actor with `website.manage` or `instructor.update`, enforce tenant identity and same-origin request checks, and audit saves.

Public instructor profiles are separate from private staff records and require explicit publication. Public mappers emit only approved professional fields, never staff email, phone, roles, invitations or account identifiers. Photo and resume media remain tenant-scoped; unauthenticated retrieval requires a matching published profile and explicit resume visibility. PDFs are served as attachments with `nosniff`. Gallery media requires an enabled matching gallery entry. Production storage remains the existing external S3-compatible interface.

Per-event and per-instructor canonical overrides are restricted to local event or instructor paths. Event OG images use local media URLs; page metadata and JSON-LD contain only validated tenant-owned public data. Admin pages are noindexed.
## Pilot production deployment boundary

The separate production Compose stack publishes only Caddy ports 80/443. PostgreSQL is on an internal Docker network without host port mapping; the app and provisioning worker run as `node`. Caddy terminates HTTPS for an explicit list of platform and tenant hosts, preserves Host, and overwrites `X-Real-IP`; application tenant lookup and origin checks still validate the hostname. Production preflight rejects test-mode markers, non-SMTP mail, HTTP object storage, missing or reused critical secrets, unlisted tenant hosts and inconsistent Google OAuth configuration. The existing runtime guards reject test mail, TEST payments and E2E Google mock outside the isolated browser harness. Real credentials live only in ignored `.env.production` or operator-managed secrets, never in the image or repository. See [DEPLOYMENT.md](DEPLOYMENT.md) for backup, restore and rollback procedures.

## Identity V2 SMS and profile boundary

Phone verification and username authentication use official Better Auth plugins. SMS delivery adapters do not verify codes or create sessions. Phones and usernames have tenant-scoped database uniqueness; phone changes require OTP. Resend, verification, source and monthly tenant delivery budgets are persisted. Delivery attempts consume budget even if the provider fails. Expired limiter cleanup preserves active quota windows.

Tenant SMS credentials use authenticated AES-256-GCM encryption with tenant/provider binding. Configuration responses omit secrets; audits contain action/request identifiers only. Provider HTTP errors are normalized without URLs, API keys, OTPs or response bodies. TEST SMS delivery is rejected in production even when E2E flags are present. There are no test SMS routes or OTP acceptance shortcuts.

Phone-created users keep an opaque non-routable internal email with emailVerified=false. UI/session DTOs hide it and mail adapters reject it. Username login requires a verified phone or verified real email without weakening real email/password verification. Login settings require a usable administrator method, and platform recovery restores email login without bypassing credentials or verification.

Profile definitions and values are bounded, tenant-scoped and validated against current definitions. National ID starts disabled and requires the dedicated high-risk permission for staff access. Account profile values remain separate from event form answers. See SMS-PROVIDERS.md for the adapter extension contract.

Account-dependent signup checks run in the Better Auth user-creation hook after the phone plugin verifies and consumes the OTP. Before phone ownership is proved, a missing/invalid code returns the same generic response for registered and unknown phones. Profile validation that depends only on the submitted form is independent of account existence. Existing-account signup payloads never overwrite credentials or profile data.

## Custom domain ownership and removal (B1)

The platform hostname from BETTER_AUTH_URL is reserved and cannot be a tenant hostname. Tenant resolution uses the normalized Host and an exact control-plane mapping; X-Forwarded-Host never selects a tenant. Percent-encoded hosts, host lists, IP literals, userinfo and malformed names are rejected. Custom registration additionally rejects ports and localhost names; IDNs store canonical ASCII.

TXT challenges use 32 random bytes, SHA-256 hashes at rest and 24-hour expiry. Rotation invalidates the previous proof. Verification checks the same hash and database expiry again at commit, preventing rotation, expiry or deletion races. TXT lookup has a five-second overall deadline and cancels its owned Node resolver. Only the issuance response to an authorized Super Admin contains the TXT value; audit records omit tokens and hashes. DNS errors expose safe messages.

Primary changes and deletion lock the tenant row and commit audit atomically. A primary domain must be verified and belong to that tenant; the previous domain remains. Primary deletion is rejected until an explicit switch, and deletion without a remaining verified primary is rejected. Domain ownership/status/primary metadata is rechecked on cache hits, including writes by another application process. The bounded cache retains the existing 15-second TTL for other metadata. These checks govern subsequent resolutions; already-running requests are not retroactively revoked. TLS routing and proxy deployment remain B3/deployment concerns.
