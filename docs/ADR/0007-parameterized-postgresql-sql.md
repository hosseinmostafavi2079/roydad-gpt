# ADR 0007: Parameterized PostgreSQL access with Prisma tenant migrations

- **Status:** Accepted; Phase 2 amendment
- **Context:** Phase 1 required explicit PostgreSQL role separation, transactional queue writes, a small reviewed SQL migration set, and provisioning across independent databases. Phase 2 explicitly requires a Prisma tenant schema and forward-only Prisma migrations while preserving the Phase 1 SQL history.
- **Decision:** Keep the mature `pg` client for runtime database reads/writes and parameterized values, with validated/quoted identifiers and the checksum-verifying Phase 1 SQL migration runner. Use a checked-in Prisma tenant schema and reviewed Prisma SQL migrations for Phase 2 tenant identity/RBAC DDL. Do not require a generated Prisma client at runtime. The tenant migration bridge recognizes the Phase 1 tenant baseline and records a Prisma baseline without resetting existing data, then applies forward-only Phase 2 migrations.
- **Consequences:** Runtime query result types remain explicitly maintained and need direct review and real-PostgreSQL tests. Prisma schema and emitted SQL both require review; migration history and the application migration registry must agree. Identifiers must never come from request input, and dynamic values must remain parameterized. Existing tenant databases must be upgraded with `pnpm db:migrate:tenants`; they must not be reset or replayed from an incompatible baseline.
- **Alternatives considered:** Moving the application to Prisma Client for all queries would add generated-client runtime coupling without being required for this phase. Using only hand-authored migration tooling would fail the Phase 2 migration requirement. Shared-schema operational data conflicts with the database-per-tenant boundary.
